# AGENTS.md — operational learnings for future sessions

## Serving, caching, and the "old UI" trap

- FastAPI serves `/` and `/static` with `_never_cache_headers()` in `src/novacontrol/api/app.py`: `Cache-Control: no-cache, no-store, max-age=0, must-revalidate` + `Pragma: no-cache` + `Expires: 0`. Every HTML/CSS/JS response must carry this trio (pinned by `test_static_html_css_js_are_never_cached` in test_web_api.py, which asserts the EXACT header value across the whole static surface: `/`, top-level assets, every `static/js/` module, and the SVG) — downgrading to bare `no-cache` allows heuristic reuse of pre-header cache entries, and a new asset type that skips the headers fails the test. Cache-bust tokens are auto-injected, never hand-written: `index.html` carries the marker `?v=__NC_ASSET_VERSION__` and the `/` route replaces it with `_static_asset_version()` (a per-request content hash of the whole static tree), so any HTML/CSS/JS edit rekeys every asset URL — mid-session edits included — with no manual `?v=` bump and no restart. Never hardcode a date token in `index.html` (`test_asset_versions_use_server_injected_marker` fails on `?v=2026`) and never delete the marker (`test_index_serves_injected_asset_version` checks the served HTML). A SECOND marker, `__NC_UI_VERSION__`, powers the visible sidebar-footer stamp (`UI v<8-hex>` in `#uiVersion`); the `/` route replaces it with the same content-derived version shortened to 8 chars, so a stale cached page shows an older stamp than a fresh load (`test_ui_version_stamp_uses_injected_marker` in test_web_platform.py guards the marker; `test_index_serves_visible_ui_version_stamp` in test_web_api.py pins that the served stamp equals the injected asset version prefix). When changing the stamp, replace the marker server-side — never put a date/version literal in index.html.
- If the user reports seeing the "old UI": the server can be provably clean (curl the root: sidebar markers + `no-cache` header + newest `?v=` token) while their VS Code/Blackbox embedded browser still shows a stale DOM it restored without refetching. The only fix is fully closing and reopening that tab. The current CSS never hides the sidebar at any width (only shrinks to 200px under 900px) — a sidebar-less render is always a stale DOM, never current code.

## Brain routing

- Scratch intent is ONE registry in `novacontrol/brain/scratch.py`: `_INTENT_ROWS` (defined after the answer builders) holds a `_ScratchIntent` row per intent — `kind`, `routing_safe`, `detect` (engine-wide predicate), optional narrow `routing` predicate (None → reuse detect), `answer` builder, `confidence`, `examples`. Two read surfaces walk it and must stay the only ones: `scratch.scratchable_intent(lower)` (NARROW — walks only `routing_safe` rows in `_SCRATCHABLE_KIND_ORDER` = greeting→math→time→conversion→knowledge→recommendation, using each row's `routing` predicate; this is the classifier that protects Explore routing) and `scratch._classify` / `ScratchReasoningEngine.answer` (BROAD — `_ENGINE_ORDER` = row order, using `detect`; covers routing_safe=False engine rows phone_control/desktop_control/capabilities). Do not unify the widths or promote engine rows into `_SCRATCHABLE_KIND_ORDER` — broad routing would send unknown "what is X" topics to a generic local reply instead of Explore research, and engine rows would swallow it. Deliberate two-width rows: time (`_TIME_PATTERNS` detect vs narrower `_TIME_ROUTING`, so "explain what year the berlin wall fell" stays research), knowledge (broad prefix/factual detect vs exact-key routing), recommendation (broad word list detect vs explicit-ask routing). Changing one behavior is a one-row edit (predicate/answer), never a parallel regex edit in two functions; `_MATH_PATTERNS`/`_TIME_PATTERNS`/`_UNIT_PATTERN`/`_TEMP_PATTERN` stay module-level because registry predicates AND answer builders share them. Routing tests are GENERATED from row `examples` (`IntentRegistryGeneratedTests` in test_brain_scratch.py walks `_INTENT_ROWS`), so new intents/answers pin themselves; examples must route through BOTH surfaces for their row (broad-only phrases like "what is dark matter" stay out of the table — those edges are pinned by the static INTENTS/narrow tests). brain.py's `_keyword_classify` imports ONLY `scratchable_intent` and interprets the name: == "greeting" → CHAT 0.9 first, == "math" → CHAT 0.88 gate right after SELF_IMPROVEMENT and before EXPLORE/PLAN, and the EXPLORE gate fires only when `scratchable is None` (no canned answer) AND a research keyword matched. Do not reintroduce separate `can_answer_directly`/`is_arithmetic_query` imports or a local `_is_greeting` set in brain.py.
- Arithmetic is routed locally through ONE predicate: `is_arithmetic_query(lower)` in scratch.py (symbolic `_MATH_EXPR`, the "add X and Y" form `_ADD_FORM`, `_FUNC_CALL_MATH` calls like "sqrt(144)", and every WORDED phrase declared in the single declarative registry `_MATH_WORD_RULES` — one (pattern, symbolic rewrite) row per spelled-out operator like "15 times 3" and per worded function like "square root of 256"/"5 squared"), used by `scratchable_intent`, `_classify`, and the answer engine. Keep ALL math detection in scratch.py via `is_arithmetic_query`, never duplicate matchers in brain.py; changing a worded operator is a one-row `_MATH_WORD_RULES` edit, never a parallel regex change. Operands may be digits OR spelled-out number words ("fifteen times three", "2 to the power of 8", "one hundred and five times two") — the operand regex only matches number-word tokens (plus `and` between them) so prose like "how many times a year" can't match, and rewrites are callables that convert captured operands via `_words_to_int` (greedy word-sequence matching, so multi-word cardinals are consumed whole). `_math_answer` translates via that same registry to a fixed point (replacing one worded op can expose a neighbor to a later rule), keeps only the two operands for the "add X and Y ..." form (`_ADD_FORM.match`) so trailing phrasing never reaches the evaluator, then turns `and` into `+`. `_classify`'s `_MATH_PATTERNS` is only the non-overlapping complement (bare symbol chains / calculate-prefix digits) — worded alternations there would be dead duplicates.
- `brain.py` no longer contains any answer-capability knowledge — all local-answer detection lives in `novacontrol/brain/scratch.py`, and greetings share one `_GREETINGS` frozenset between `scratchable_intent` and `_classify`.

## Frontend structure and flows

- `/ask` returns one flat envelope `{route, intent, summary, data}` where `data` is the handler payload directly — never nested, and never under a `payload` key again (old `payload.payload`/`decision` wrapping and the envelope key rename are gone; do not reintroduce `payload` on the wire). Chat answers can still be full Explore reports; `renderChatResult` unwraps the envelope ONCE (`const payload = data.data || data`) and delegates report shapes to `tryRenderResearch` in `render-explore.js`, which now takes one unwrapped body and only checks whether it has report fields (`overview`/`key_points`/`sources`/`videos`) — the old `[data.payload, data, data.report]` candidate probe is gone. Flat endpoints (`/explore`, `/command/plan`, `/system/health`) return the payload with no envelope at all; renderers that can only receive flat bodies (e.g. `renderBuild`) keep `data.data || data`-style fallbacks, but nothing probes `data.payload`/`data.report`/`value.payload` anymore (pinned by `test_no_envelope_payload_sniffing_remains`).
- Chat history survives reloads via localStorage (`novacontrol.chatHistory`, capped at 30 turns): `submitChat`'s `run` `onSuccess` records `{role, text, route}` (assistant text via `chatTextForHistory` in app.js), and init calls `renderChatHistory()` to replay bubbles with `appendMessage` — which was previously dead code and is now the shared history bubble renderer (keep it in sync with the shared markdown rule below). The active panel also persists (`novacontrol.activePanel`, restored by `restoreActivePanel()` which must run AFTER `setupTabs`). `renderChatResult` appends the user's question bubble before the answer page so the thread reads as a conversation; the answer page itself still replaces per-turn (single-turn design). "Clear Chat" (`clearChatButton`) removes the localStorage key, wipes the `#chatStream` DOM, AND posts `/chat/clear` (brain.conversation.clear()) — all three, or the LLM keeps old context.
- Brain mode (local scratch ↔ local LLM switch) has ONE source of truth: `NovaBrain.mode` (`auto|llm|scratch`), mutated only by `NovaBrain.set_mode` — brain.py owns the provider hot-swap (scratch swaps Echo in, llm re-arms the boot provider, auto restores it); `NovaControlApplication.set_brain_mode` mirrors the mode into `UserSettings.brain_mode` (persisted via the settings store), re-syncs Explore via `_sync_explore_provider` (the `on_provider_upgrade` callback is ALSO wired to `_sync_explore_provider`, so a lazy Ollama upgrade keeps Explore pointed at the live provider — never restore the old direct `set_completion_provider(provider)` lambda), and gates the lazy re-probe: `_maybe_upgrade_provider` returns early when `mode == "scratch"`, so auto-detection can never override a forced scratch. `effective_mode` is derived from the LIVE provider (`llm if model_configured else scratch`), never from the chosen mode — forced "llm" with no model must report scratch honestly. Boot order matters: settings load BEFORE the brain is constructed so a persisted scratch mode is honored from the first answer. UI: the Chat panel header's `#brainModeSwitch` select posts `/brain/mode`; `syncBrainSwitch()` (called from refreshStatus) re-reads the persisted server mode so the switch survives reloads. Task deletion: TaskCenter.delete/clear + `/tasks/delete` (404 on unknown id) + `/tasks/clear`; BOTH `/status.app.tasks` and `GET /tasks` return TRIMMED views (id/title/kind/status/created_at — never TaskRecord.to_dict(), whose `result` embeds whole response payloads); renderTaskList (render-panels.js) renders rows with per-row Delete buttons and `#clearTasksButton` in the System panel.
- `dom.js` owns the only Markdown renderer (`renderMd` + inline `_renderInline`); Chat AND Explore rendering go through it — never add a second renderer. Every free-text path must route through it: chat lead/message (`renderMd`), `appendMessage` bubbles (`renderMd`), `payload.content` (`renderMd`), and list items via `richBullet` (which calls `_renderInline`). A text node still showing raw `**`/backticks means a renderer bypass was introduced.
- Chat-answer text policy has ONE owner: `extractAnswerText(value, fallback)` in state.js (precedence: string → unwrap the `/ask` `data` key when it is an object → `message` → `answer` → `content` → `overview` → `summary` inside data, then the same fields at top level; trims, scrubs leaked `Payload:`/`Intent:` routing text, returns `fallback` when empty). NOTE: the `content` branch is REACHABLE — the /ask agent fallback (`_handle_agent` → `AgentResponse.to_dict()`, route "agent") ships a content-only payload `{task_id, agent_name, role, status, content, metadata, brain_mode}` with NO `message`; the inner-data scan hits `content` before the envelope `summary`, so deleting the branch would degrade every agent answer to the "I completed the request." fallback (pinned by `DataContentReachabilityTests` in test_web_platform.py). Keep it while that handler speaks `content`. `textForSpeech`, `cleanSummary` (render-utils.js, adds the "I completed the request." default), `renderChatResult`'s lead, and `chatTextForHistory` (app.js) all delegate to it — never re-derive field precedence at a call site again. `renderGeneralAiPage` (render-panels.js) must never read `payload.message`/`payload.content` as answer text either: the lead (`summary`) is the only place the answer renders, and the section below the heading is STRUCTURE ONLY (suggestions/plan/sections/actions, else the neutral placeholder). Raw field reads there re-leaked scrubbed `Request:`/`Intent:` text (the `payload.message !== summary` guard fired on sanitizer deltas) and duplicated content in the lead+body. The precedence is pinned behaviorally: `ExtractAnswerTextTests` in test_web_platform.py evals the REAL state.js + render-utils.js in Node (skipped cleanly when node is absent) against a 14-row table; a static test also forbids the removed `payload.message || payload.content || data.summary` / `payload.answer || payload.message` chains from returning. Gotcha when embedding JS in such a test: emit each expression with `json.dumps(expr)` so node stores the SOURCE as a string and `eval`s it in the loop — emitting it raw evaluates at array-build time, turning `expr` into the result (then `eval(result)` parses the answer text as code, e.g. "Unexpected identifier 'completed'").
- DOM-level JS renderer tests follow ONE harness pattern (see RenderGeneralAiPageDomTests in test_web_platform.py): read the REAL static scripts (dom.js/state.js/render-utils.js/render-panels.js — load in index.html order, never app.js whose top level binds events), prepend a minimal DOM shim (createElement/createTextNode/createDocumentFragment, appendChild with fragment-splicing, classList, textContent recursion, a walk-based qsa for `.class` and bare-tag selectors only), and eval shim + scripts + driver together in ONE sloppy-mode eval so function declarations AND shim consts share scope. The driver calls the real renderer and `console.log`s JSON.stringify(inspection) — forgetting the console.log yields empty stdout and a confusing JSONDecodeError in the test (wrap stdout parsing). Use this pattern for any future "renderer must never leak X / must render Y exactly once" pin; a static source-substring test is NOT a substitute — mutation-test the harness once (re-introduce the forbidden raw read, watch the right tests fail, restore) before trusting it. `.format()` on the shim template means literal braces are doubled — keep new shim code doubled.
- JARVIS desktop verification (desktop/controller.py): OPEN_APPLICATION polls `_wait_for_window` (Windows: `Get-Process` MainWindowHandle enumeration, matched via `_window_stem`/`_window_matches`) and raises `VerificationError` when no window appears in 8s — a launch that never shows a window now surfaces as FAILED, never "Executed successfully". `_wait_for_window` returns `{}` when the probe ran but nothing appeared (empty dict, NOT False — its annotation is `dict | None` and mypy is clean), `None` only when the probe is unavailable. TYPE_TEXT on Windows stages the exact text via clipboard + Ctrl+V, then `_verify_type_windows` confirms the payload reached the clipboard AND a window is focused before success; apostrophes are PS-escaped by doubling (`''`), NOT backtick-replaced (the old `replace("'", "`")` silently pasted backticks). Probes returning None (non-Windows/unavailable) skip verification rather than fail. Tests stub the OS probes via `ProbingRunner` (tests/test_desktop.py) so nothing touches the real desktop.
- Desktop, browser, AND phone automation share ONE audit trail: `core/audit.py` (`AutomationAuditLog` protocol + `InMemoryAutomationAuditLog`, re-exported from all three subsystem packages). Each controller takes an optional `audit_log` constructor arg (default in-memory) and `execute_action` appends EVERY result — denied, completed, failed — exactly once before returning (desktop/browser assign `result` on all paths then append after the try; phone mirrors that shape — do not re-add `return` inside the try, it bypasses the trace). `PhoneActionResult` satisfies the `AuditableResult` protocol structurally (same five fields, StrEnum status). Audit parity is pinned three ways: `PhoneAuditTests` (test_phone.py) mirrors the desktop/browser audit tests (approved/denied/failed traces with `datetime.fromisoformat` timestamps).
- Phone commands cover FOUR phrasing families — open-application, send-text, call, screenshot. ONE parser owns the split: `parse_phone_command` (application_helpers.py) returns (kind, argument) with kind in `open|text|call|screenshot`; `plan_phone_command` maps each kind to its controller planner (`plan_open_application` / `plan_send_text` / `plan_call` / `plan_screenshot`) so the workflow carries the right `PhoneActionType`. `resolve_phone_target` survives only as a thin wrapper (delegates to parse, returns the open-target). Routing mirrors the SAME families in TWO kept-in-sync places: `_looks_like_phone_command` (brain.py) and `_phone_control_match` (scratch.py row `phone_control`, `routing_safe=False`, engine-only) — both use device-word-anchored OR bare-verb logic (`call `/`dial `/`text `/`sms ` prefixes + `take a screenshot` phrases; whatsapp alone suffices, it is a phone-only app). New example utterances in the scratch row are auto-pinned by `IntentRegistryGeneratedTests` (both surfaces must agree). Runner safety: SEND_TEXT uses ACTION_SENDTO (sms_body pre-fill) and CALL uses ACTION_DIAL — the phone user still presses send/call on the device, so nothing transmits without on-device confirmation; SCREENSHOT is `exec-out screencap -p`. Message specs split via `_phone_message_parts` (shapes: `to X say Y`, `X saying Y`, `X: Y`; free text without a separator stays whole as the body with empty recipient).
- Desktop, browser, AND phone automation share one token flow: `/command/plan` (or `/desktop/plan`, `/phone/plan`) mints a single-use, 5-min token (`application.py: _mint_approval/_consume_approval`) and `/command/execute` re-dispatches on the brain intent, so a plan rendered in Chat or the Command panel approves correctly for all three devices. The three executors share `_execute_planned_command` (application.py) — token validation lives in each public `execute_*_command` (distinct error wording), the rest (consume → `_workflow_from_plan` → gateway swap → run → mark executed) is one helper taking controller + model classes + `result_label`. Do not fork the execute bodies again. The in-output "Approve And Run" button in `render-panels.js` must keep posting to `/command/execute` — posting to `/desktop/execute` silently breaks browser plans (it rebuilds the workflow as a desktop workflow). `plan_browser_command` parses navigate/fill-form phrasing (`parse_browser_command` in application_helpers.py) and returns a `not_an_action` envelope without a token when nothing parses.
- DECISION — execute-without-token returns 200 (not 403) in exactly two cases, both load-bearing for the web UI, which never calls `/phone/*` directly: (1) `/phone/execute` with no paired bridge returns the pairing plan (`waiting_for_phone_bridge`, 200) because `render-panels.js` renders the "Pair needed" card + `bridge.next_steps` guidance from it — a 403 would show a bare error toast instead of telling the user how to pair; (2) `/command/execute` on a non-device command returns the `not_an_action` envelope (200) whose browser message suggests the exact phrasings that DO work ("navigate to…", "search the web for…"). Everything else is strict: missing/expired/replayed token on desktop/browser execute → `ValueError` → HTTP 403 (pinned by TokenGateTests in test_web_api.py; phone gate fires only when a bridge IS available). Do not "fix" the two 200 paths to 403 for consistency — they are the UI's guidance channel, not a security hole (no token means nothing runs). If either ever changes, `rememberApproval`'s waiting_for_approval-only guard means no approval is stored from them; but the pairing guidance and not_an_action suggestions are consumed by the renderers and would degrade to error toasts.
- `NoopBrowserRunner` (src/novacontrol/browser/controller.py) must mirror `PlaywrightBrowserRunner`'s classmethod `is_available()` — `NovaControlApplication.status()` calls it on the class, and the HTTP tests patch the name with `NoopBrowserRunner`, so missing it fails every `/command/*` TestClient test with AttributeError. Static asset paths: `app.js` is at `/static/app.js` (top level) while its modules live at `/static/js/*.js` — a test requesting `/static/js/app.js` gets 404.
- Live progress is ONE SSE activity channel, `GET /events/stream` (`api/app.py`), which relays the APP-WIDE `nova.event_bus` to the page — there is no per-request `/explore/stream` endpoint and never reintroduce it (it hot-swapped `nova.explore._event_bus` per request, a concurrency hazard). The bus feed is wired up in application.py: `ExploreService` is constructed with `event_bus=self.event_bus` (its research steps publish `explore.progress`), and the shared `_execute_planned_command` passes a `progress` coroutine into the desktop/browser controllers' `execute_workflow(workflow, progress=...)` hooks (both controllers accept the optional kwarg and announce "Running action i/n: …" before each action) so approved commands publish `command.progress`. `EventBus.unsubscribe` (core/events.py) exists for the SSE subscriber; every connected client adds one wildcard handler and MUST unsubscribe in the generator's finally.
- `run()` in `render-utils.js` owns loading/error/toast/button state for EVERY action AND the activity window: while a run is loading, `state.activity = {family, targetId}` (families: explore→`explore`, command→`command`, chat→`ask` which accepts BOTH explore and command steps since a chat answer can be research or an approved action). One `EventSource` per page (`connectActivitySource()` in render-utils.js, called from app.js init) listens for `explore.progress`/`command.progress` and `appendLiveStep` renders each `detail` under run()'s loading scan-line (container `.explore-progress`, rows `.progress-step`). EventSource cannot send an Authorization header, so the endpoint also accepts `?token=`; the UI passes the tokenInput value. Never give an individual action its own SSE/reader again. Explore's task is now just `requestJson("/explore", body)` resolving with the report — live steps arrive via the channel while it runs. `run()`'s double-click guard runs AFTER the caller's synchronous prelude — only flows that clear their input before calling `run()` need their own guard first (`submitChat` does because it clears `chatInput`; Explore doesn't clear its input).
- Voice (voice.js): Web Speech fires `onend` after every `onerror`, so an error status that doesn't survive `onend` silently reverts to "Voice ready" — the exact "mic blocked but UI says ready" bug. `state.voiceError` holds persistent failure codes (`not-allowed`/`service-not-allowed`/`security`/`audio-capture`); `onend` re-asserts the error headline while set, and only `onstart` (real mic acquisition) clears it. Transient codes (`no-speech`, `network`) flash guidance but don't hold the error state. Voice notices carry class `voice-notice` and the latest replaces older ones — keep the dedupe if a new call site is added.

## Commands and environment (Windows/Git Bash)

- Pure Python uvicorn app — there is no package.json, never try npm. Server: `python -m uvicorn novacontrol.api.app:create_app --factory --host 127.0.0.1 --port 8000`. `.venv` has an editable install, so edits in `src/novacontrol` are live on restart.
- Tests and mypy need `PYTHONPATH=src`: `python -m pytest tests/ -q` (full suite ≈305 tests + 295 subtests), `python -m mypy src --ignore-missing-imports`.
- Port 8000 is the user's own run target — stray session servers on it cause `[Errno 10048]` when the user starts theirs. Clean up session servers on 8000; use 8001 for previews.
- Explore query layer (src/novacontrol/explore/query.py): `is_relevant` is shopping-aware — `detect_shopping_context` (price/currency/amount or ≥2 commerce words) triggers a stricter gate where qualifier words (`budget`, `under`, amounts) cannot carry relevance alone and a real product token is required, so fiscal pages about "the budget" never leak into "best budget laptops under 500". Function words are stripped from relevance tokens with a fallback to the loose check when no content token exists. `build_search_queries` re-anchors the price phrase (e.g. `under 1000`) because `extract_search_topic` can clip amounts. `_safe_search` in service.py applies `is_relevant` to Wikipedia fallback results too. All pinned in test_explore.py's ShoppingQueryContextTests. The synthesizer's fact-density guarantee (definition-heavy, cause-heavy, and single-fact snippets never degenerate to a bare intro shell for any query kind) is pinned by tests/test_synthesizer.py — do not remove each builder's `_any_facts` fallback, that machinery is the guarantee.
- Git Bash mangles `$` inside double-quoted PowerShell commands (`$p`, `$_` get eaten) — single-quote PowerShell from bash. `Start-Process` detach may time out the tool wrapper while the process survives: then verify port/PID instead of retrying. The `code_search` tool intermittently fails (missing vendored ripgrep) — fall back to `grep`/`sed` via the terminal.
- Ollama auto-detection happens at boot AND lazily per chat: `build_llm_provider_from_environment` (in `integrations/llm.py`) probes `http://127.0.0.1:11434/api/tags` at app boot, and when that yields the Echo fallback, `make_ollama_reprobe()` (wired in `application.py`) probes again on each chat request — rate-limited to one 2s probe per minute of misses, upgraded once and cached for the process lifetime, probe runs via `asyncio.to_thread`. On a hit, `NovaBrain._maybe_upgrade_provider` (start of `chat()`) hot-swaps `brain.completion_provider` and fires `on_provider_upgrade` → `explore.explainer.set_completion_provider`, so Chat answers AND Explore LLM synthesis upgrade without a server restart (the System panel's AI Brain card reflects it on the next /status). A configured LLM or disabled env never probes; a broken probe never breaks chat. Override/disable with `NOVACONTROL_OLLAMA_URL` / `NOVACONTROL_DISABLE_OLLAMA` (conftest.py sets DISABLE process-wide so suites are deterministic on Ollama hosts — detection tests pass explicit environ instead). The Ollama base URL must be the ROOT (no `/v1` suffix): `OpenAICompatibleLLMProvider.complete` appends `/v1/chat/completions` itself, and a `.../v1` suffix doubled to `/v1/v1/...` (404) — that regression is pinned by `tests/test_integrations_llm.py` (which also pins the reprobe: disabled-env miss, miss→rate-limit→hit→cached-same-object). Both factories treat an explicitly passed EMPTY environ as authoritative — `os.environ if environ is None else environ`, never `environ or os.environ` (an empty dict is falsy and would leak the host env back in).
- Cloud LLM (ChatGPT/Gemini/Groq/OpenRouter/Mistral/DeepSeek) is a THIRD brain tier alongside scratch + local Ollama: `CLOUD_LLM_PRESETS` in `integrations/llm.py` is the single registry (one row per OpenAI-compatible endpoint; Gemini's preset uses chat_path `/v1beta/openai/chat/completions`; Anthropic is deliberately absent — its `/v1/messages` wire format is NOT OpenAI-compatible and needs its own provider class). `build_cloud_provider(provider_id, api_key, model, environ)` is the only constructor; `NovaBrain._cloud_provider` is a SEPARATE slot from the boot provider so local ↔ cloud switches never lose either config, and `set_mode("cloud")` with nothing installed behaves exactly like "llm". `NovaControlApplication.set_cloud_llm/clear_cloud_llm` persist `{provider, api_key, model}` via the state store namespace `cloud_llm` (gitignored runtime data) — the raw key NEVER travels back over any API: responses carry `api_key_hint` = redacted tail only (`_redact_key`), and `clear_cloud_llm` must wipe the store too. Endpoints: `GET /brain/cloud/presets` (metadata, no secrets), `POST /brain/cloud` (422 on unknown provider / empty key), `POST /brain/cloud/clear`. UI: Settings panel's cloud card (`#cloudProvider/#cloudModel/#cloudApiKey`, `setupCloudLlmCard` in app.js) + the `Cloud LLM` option in the Chat-header `#brainModeSwitch` (selecting it unconfigured jumps to Settings with a toast). Installing/clearing must `refreshCloudStatus()` AND `refreshStatus()` so the switch + AI Brain card follow. ChatCloudRoundTripTests (test_brain_mode_and_tasks.py) spins a fake OpenAI-compatible HTTP server and pins the wire contract (path, bearer key, model).

- `waiting_for_phone_bridge` is a DISTINCT blocked state in the web UI, never a plain approval: `renderCommand` checks `data.status === "waiting_for_phone_bridge"` FIRST and renders `bridgeBlockedCard` (amber card, ALL pairing `next_steps` via `richBullet`, explainer that approval is not the missing step) instead of the approval banner, and suppresses the inline Approve And Run even when a stale plan carries a token — the state check gates the button, never token absence alone (pinned with a token-carrying blocked fixture in `RenderCommandBridgeBlockedTests`, which drives the real render-panels.js against the DOM shim). The JARVIS Phone panel's header Approve And Run mirrors this: `setJarvisRunAvailability` (app.js) disables it on a blocked plan/`phoneStatus` and re-enables on any token-bearing plan, executed result, or available bridge — a blocked plan carries no token, so header-disabled + card guidance is the only coherent pairing.
- JARVIS panel (J.A.R.V.I.S) is the unified DEVICE-PINNED surface: ONE sidebar tab with a Desktop/Phone device switch (`jarvisDeviceDesktop`/`jarvisDevicePhone`, persisted as `novacontrol.jarvisDevice`), one shared input/output, and endpoints chosen by the active device — Desktop posts `/desktop/plan` + `/desktop/execute`, Phone posts `/phone/plan` + `/phone/execute` (NEVER `/command/*` — the pinning is the point: a phone phrase must not classify onto the desktop controller). Approve And Run posts the device execute endpoint with the token from the last preview of that exact command (`approvalFor` reuse + one re-plan on expired token, mirroring `commandRunButton`). `renderCommand` renders BOTH device plan shapes (steps/approval for desktop, bridge card + results for phone) — do not fork it. GET `/phone/status` and POST `/phone/connect` are NOT plan shapes: they render through `renderPhoneStatus` (render-panels.js, mirrors the bridge card) via the `phoneStatus` render type — never route them through `renderCommand` (desktop-shaped "No command text" fallback) or `renderGeneric` (textForSpeech drops `next_steps` pairing guidance). `/phone/connect` runs the bridge pairing flow (controller `connect()` → runner `connect()`: starts ADB + probes devices so the phone shows its RSA prompt; without adb it reports install steps — it NEVER executes a phone action). Quick chips fill the panel input and plan; phone-only controls carry class `phone-only` and are hidden on the desktop device; ids: `jarvis{Input,PlanButton,RunButton,Output,DeviceDesktop,DevicePhone,VoiceButton,PhoneConnectButton,PhoneStatusButton,History,HistoryList,HistoryClearButton}`.
- JARVIS desktop parsing (`parse_desktop_command`): chains split on EVERY ` and ` with verb-aware re-merging, so "search for cats and dogs" keeps one query while "type hello world and press enter" becomes three steps (type/press are new step kinds; `press` → KEYBOARD_SHORTCUT). The `search` step plans WEB_SEARCH (`plan_web_search`), NOT SEARCH_START_MENU — `plan_command` passes the enclosing browser from a preceding `open <browser>` step via `_BROWSER_LAUNCH_NAMES` so "open chrome and search for cats" opens the results URL in a Chrome tab (the old behavior keystroked the query into the Windows Start Menu). `_web_search` builds a Google results URL and launches it like any target. Spoken app names resolve through `LocalDesktopRunner.APP_ALIASES` + `_resolve_app_target` (steam→steam://open/main, mail→mailto:, settings→ms-settings:, files/folder→explorer.exe, office apps→their exes); URI-scheme targets launch through `cmd /c start`'s protocol handling — `shell=False` there is intentional, keep it. Unknown names and explicit paths pass through unchanged.
- JARVIS command history lives in localStorage (`novacontrol.jarvisHistory`, cap 30, newest last): every plan/execute records via `recordJarvisHistory` (an immediate repeat of the same command UPDATES the last row's status instead of duplicating); each row has its own Delete button (`data-delete-jarvis`) and `jarvisHistoryClearButton` clears all — both re-render from storage, never from a parallel in-memory list. JARVIS voice (`jarvisVoiceButton`, `setupJarvisVoice`) owns a SEPARATE SpeechRecognition instance from the chat voice — final transcripts fill `jarvisInput` and immediately run the same plan flow; do not reuse `state.recognition`.

- Agentic architecture (`agentcore` package, docs/AGENTIC_ARCHITECTURE.md): `AgenticOrchestrator.run_task()` runs interpret → plan → perceive → act → observe → verify → recover → learn, composing the EXISTING controllers (browser/desktop runners, explore research, vision) — never fork them. Non-negotiable invariants: the Verifier distinguishes *executed* from *completed* and refuses to pass on "actions exist"; OBSERVE steps are perception, never verified against their own description (that spiraled the recovery loop once already); destructive actions and missing-dependency errors ABORT recovery (retry cannot install a package); interpreter LLM-enrichment is skipped for echo/deterministic providers (parsing an echoed prompt injects it as subtasks). Application knowledge (`data/agentic_knowledge.json`) carries confidence with freshness decay — low-confidence paths are never proposed. Perception layer 1 rides `MultimodalVisionProcessor` wired to the LIVE brain provider (`_build_vision_processor`), so installing an Ollama vision model (llava) upgrades screen understanding with zero code change.

## Reliability, lifecycle events, and the capability registry (staged phases 8–9)

- `src/novacontrol/reliability/` is the newest package and composes existing abstractions rather than replacing them: `VerificationEngine` subclasses the planner's `DeterministicVerifier` (the step's own check → a per-tool strategy → the check the action implies; window/network probes are injectable and answer "cannot tell" instead of failing), `RecoveryEngine` wraps `RecoveryAdvisor` inside the plan's retry ceiling (a destructive or external action and a refusal are never retried), `TaskStateMachine` checks all eleven transitions — an illegal one RAISES instead of overwriting — with cooperative cancellation at checkpoints, and `PermissionManager` is one ordered layer (declared → `ToolMetadata` → action verb → LOW) that reports which source decided. Wire new behavior through these; never add a second verifier, retry loop or risk table.
- Event payloads must not shadow the envelope's reserved kwargs `source`, `correlation_id` or `causation_id` — `Event.of`/`Event.child` raise `InvalidEventPayloadError`, and a publisher that swallows the raise makes its event silently disappear (`tool.selected` shipped once with a `source` payload key and never fired). `vision.*` uses `image`; `tool.selected` uses `selection_source`. Publishing goes through a seam injected at construction (observer / sink / announcer), never a direct `event_bus` lookup, and `EventBus.emit` (not `publish`) is the door that cannot raise. The request id lives in the `_CURRENT_REQUEST` ContextVar so nested work inherits correlation.
- Capability availability is a property of the MACHINE, not of the request: the decision engine and the tool selector report it but never re-route on it. `CapabilityRegistry`'s projected tools are read live from the attached catalogue's `registered()` on every read (never a boot snapshot), `for_intent`/`best` stay DECLARED-only, an unprobeable requirement reports UNKNOWN rather than "available", and a declared-but-unwired capability is reported as exactly that (`system.reason`).
- `NovaControlApplication._HANDLERS` must stay a per-instance copy (`dict(type(self)._HANDLERS)`) — as a class attribute, one test's injected handler re-routed every other application in the process (16 failures in `test_web_api.py`).
- A new route is done in five places: the handler in `api/app.py`, the `ApiSurface` row in `api/models.py`, the consumer declaration in `api/route_consumers.py`, the regenerated `docs/API.md`, and a test — `python scripts/generate_api_reference.py --check` fails CI otherwise.

## User preferences

- The user reports stale UIs aggressively and values deletion: prefer deletion-first passes and explain what was removed, not just what was added. Changes to the visible UI must be re-verified live after a reload, not asserted.
- Vision-guided desktop control (desktop/vision.py + desktop/vision_guide.py): `VisionController` composes the desktop controller — `describe_screen()` captures + understands (MultimodalVisionProcessor when a provider is wired, honest window-probe fallback otherwise), `guided_click(label)` locates the element (LLM region → OCR band → UI landmarks, in that order), clicks, and reports verification with `changed: None` when it cannot verify (never a guessed success). Every failure or unverifiable result is recorded to the shared `BugLog` (core/buglog.py, data/bugs.json, what/where/when, open|fixed status, mark-fixed + clear-fixed). API: `GET /vision/status`, `POST /vision/describe`, `POST /vision/click {label}`, `GET /bugs`, `POST /bugs/{id}/fix`, `POST /bugs/clear-fixed` — all registered in BOTH api/app.py and the ApiSurface registry (api/models.py), whose exact set is pinned by BackendFrontendContractTests.
- In-app desktop chains (desktop/controller.py): step kinds now include `navigate` (app deep-link via `_APP_NAVIGATION_ROUTES`: steam://open/library, ms-settings:<page>… — `_app_navigate` keeps "open steam and go to library" off the Start-Menu surface), `click` (vision-guided VISION_CLICK: locate → cursor → click → before/after screenshots, fails honestly when the element cannot be located), and `stop` ("stop that" / trailing "and stop" targets the last opened app; STOP_APP sends WM_CLOSE via PostMessage — graceful, never taskkill). Spoken user folders ("open downloads/documents/pictures/music/videos/desktop") map to `%USERPROFILE%\<Name>` and `_open_folder` expands env templates via `os.path.expandvars` (and never mkdirs a missing path — that behavior was removed).
- Auto-approve & run: `UserSettings.auto_approve_run` (default False) + Settings checkbox (`#autoApproveRun`, mirrored into `state.autoApproveRun` on load/save). When enabled, a planned tokened command executes immediately through the SAME approval flow: `jarvisPlan`/command plan register the execute callback in `window.runAutoApproved[command]`, and `renderCommand` fires it once when a `waiting_for_approval` plan with a token renders (single-shot delete before invoke). The plan preview still renders — the gate is skipped, not the visibility.
- The Command tab's composer is "Quick Command" (renamed from the duplicate "Jarvis Command"); the standalone "JARVIS" nav section label was deleted (the J.A.R.V.I.S tab itself remains — it is the device-control surface). Vision panel: sidebar tab `visionPanel` with Describe Screen (`visionDescribeButton`), Guided Click (`visionClickInput`/`visionClickButton` → `visionDescribeOutput`), and the Bug Log list (`bugList`, `bugRefreshButton`, `bugClearFixedButton`, `bugOpenCount`; rows reuse `.jarvis-history-row/-main/-text/-meta/-delete` styling with a Mark-fixed button).
