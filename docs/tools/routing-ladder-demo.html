NovaControl · change explained

One pipeline, one owner per decision.

A shape-only restructure of how NovaControl routes a request to an intent (backend) and renders the answer (frontend). No features were added; behavior was preserved and then adversarially re-verified. This page walks the design, the proof, the one regression found, and the merge risks that remain — plus the overhaul addendum that closed the worded-math gap.

The merge, proven equivalent

Before: two separate checks at rung 3 — research-words ∧ ¬scratchable, then “what is” ∧ ¬knowledge-key ∧ ¬scratchable. The knowledge-key test was redundant (it is a subset of the scratchable test’s own key loop), so the second check was really just “what is” ∧ ¬scratchable.

old  (E ∧ ¬S)  ∨  (W ∧ ¬S)  ≡  (E ∨ W) ∧ ¬S  =  new

Same trigger words, same confidence, same position in the ladder → identical outputs on every input; brain.py now holds zero knowledge of math/time/units/knowledge-keys.

3
Two classifiers, one policy owner — on purpose

    
scratch.py now owns every “can I answer this without a model or the web?” decision. There are two of them, and they are deliberately different widths. Confusing them is the trap a future session could fall into.


    

      

        
can_answer_directly() · narrow

        
Used by routing. Only counts queries with a canned local answer:

        
    
          
  • math — symbolic 15*3 or worded 15 times 3
    • 
          
  • time/date · unit & currency conversion
    • 
          
  • exact knowledge-key hit — how many planets
    • 
          
  • recommendation / movie / book / food prefixes
    • 
        

        
“what is quantum computing” → NOT answerable → correctly goes to EXPLORE for a real web answer.

      

      

        
_classify() · broad

        
Used by scratch.answer() when a request already landed in CHAT. Best-effort local:

        
    
          
  • adds greetings, capabilities, phone/desktop stubs
    • 
          
  • treats any “what is X” as knowledge
    • 
          
  • if no fact matches → generic reply that points to Explore
    • 
        

        
Broad is fine here — this only runs after routing already decided CHAT.

      

    

    
Constraint — do not unify them
      If routing used the broad classifier, “what is quantum computing” would classify as knowledge → routed to CHAT → answered with a generic “use Explore” line instead of real research. The two widths are the design, not debt.


    
Addendum — worded math closed by the overhaul
      One shared math detector in scratch.py powers both classifiers: symbolic 15*3, spelled-out operators (times · plus · minus · over · multiplied by · divided by) and the “add 5 and 7” form, plus trailing-punctuation handling. Live check: “what is 15 times 3” → route chat, message “The result of `15 times 3` is 45.” — where it previously ran an Explore web search that never said 45. Routing still delegates to scratch; brain.py holds no math knowledge.

  


  
  

    
4
Frontend: three wrappers → one, and one render gate

    
Chat submit, Explore research, and every action button each hand-rolled the same loading/error/toast/button-state dance. Now run() owns it and flows pass per-flow options. And “is this a research report?” is answered in exactly one file.


    

      

        
before · submitChat (~20 lines)

        
// duplicate of what run() already did…
guard; read input; empty-check
state.lastQuery = request
setButtonLoading("askButton", true)
renderLoading("chatStream", "Thinking…")
clearInput()
requestJson("/ask")
  .then(render + toast "Response ready")
  .catch(renderError; reset voice)
  .finally(unload)      ← Explore handler & 12 buttons copied this shape

      

      

        
after · submitChat delegates

        
guard before clearing input   // ← the fix, §4b
read input; empty-check
state.lastQuery = request; clearInput()
run("chatStream", "chat", fetch, "askButton", {
  loadingText: "Thinking…",
  successToast: "Response ready",
  onError: resetVoice,      // flow-specific bits stay here
})

      

    


    

      
The render gate — who may draw an Explore page

      

        
CallerPathOwner of “is this a report?”

Before: renderChatResult re-derived the report shape itself. Now the sniffing lives in one file and Chat simply delegates — if the shape logic changes, it changes in one place. (The former one-use extractResearchReport helper was inlined here by the prune pass.)

    


    

      
The one regression the adversarial pass found · double-click ordering

      

        
click 1
guard passes → reads text → clears the input → run() sets loading → fetch starts

        
click 2
no handler guard anymore → reads input = “” → toast “Type a message first” while request 1 is in flight — misleading feedback

        
fix
restore the 1-line guard before clearing: click 2 now returns silently · exactly one /ask (verified in network log) · Explore needs no guard because it never clears its input

      

      
Rule that falls out: run()’s guard runs after the caller’s synchronous prelude — any flow that mutates its input before calling run() needs its own guard first. That ordering hazard is why this class of bug ships silently: no test can see it, only an ordering read.

Validation evidence & the real merge risks

    
What actually proves the change, and what still needs doing before this is safe to ship — calibrated to this restructure, not a generic checklist.


    

      
Evidence gathered

BLOCKER · process
No git baseline exists
The repo has zero commits — everything is untracked. Nothing can be diffed, reverted, or bisected. Act: initial commit now, then commit this change separately so it is one reviewable unit with a rollback point.

      
BLOCKER · validation
Frontend has no automated tests
run() is now a shared choke point for 12+ bindings; only node --check + manual probing guard it. Act: run the smoke list against the Docker-built image (chat math, chat→research, explore, command plan, health, settings, double-clicks, reload-mid-research) before merge.

      
HARDENING
Routing proof rests on reasoning + ~26 pinned utterances
Equivalence is exact, but no table row pins cross-intent boundaries. Act: add rows like “compare the plan”, “what is the plan” (must stay EXPLORE, before PLAN) to freeze the merged rung against future drift.

      
HARDENING
Unpinned FastAPI + private StaticFiles override
fastapi>=0.115 resolves “latest” at Docker build; a future Starlette change could silently break the no-cache override. Act: pin resolved versions + a deploy-time curl assertion that / and /static/* return cache-control: no-cache.

      
ROLLOUT NOTE
Open tabs keep the old UI
Embedded webviews restore the last DOM without refetching — deploy won’t visibly change already-open tabs; users must close and reopen. Data/schema untouched; API routes & payloads unchanged, so no consumer-compat or migration work.
